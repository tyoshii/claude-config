# /test-prune [対象パス] [report]

AI 生成テストの間引き。テストの数を減らすこと自体は目的ではない。
「壊れたら落ちるべき振る舞い」を守ったまま、重複・無意味・脆いテストを除く。

分類表・保護対象・背景は `$SKILL_DIR/references/categories.md`。

## 引数

| 引数 | 説明 | デフォルト |
|------|------|-----------|
| `対象パス` | 間引く範囲（例: `src/foo`、`packages/api`） | リポジトリ内の単体テスト全体 |
| `report` | フェーズ2（提案）で止め、適用しない | 指定なし（承認後に適用まで進む） |

## 変更してよい範囲

- テストファイルとテスト用ヘルパー（フィクスチャ・ファクトリ・テストユーティリティ）だけ
- **本番コード・依存（manifest / lockfile）・CI 設定には触れない**。カバレッジや変異テストの
  ツールを入れたいときも、入れずにフェーズ2で提案する

## 絶対に守ること

1. 削除・統合の前後で、行カバレッジ・分岐カバレッジを下げない。下がる変更は取り消す
2. 変異テスト（Stryker / mutmut / PIT / go-mutesting 等）が導入済みなら、削除前に殺せていた変異が
   削除後も殺せることを確かめる。カバレッジは「実行された」しか示さず「検証した」は示さない
3. 保護対象（`references/categories.md` の「保護対象」）は削除しない。統合・書き直しは可
4. 「たぶん重複」では消さない。消す根拠（どのテスト・どの層が同じ保証をしているか）を 1 件ずつ言えないものは残す
5. 禁止: テストを通すための本番コード変更 / assert を弱めて統合したことにする（存在確認・真偽だけへの置換、
   スナップショット化）/ skip・todo・コメントアウトで件数を減らす

## 実行手順

### 0. 開始前

- `git status --short` で未コミット変更を確認する。テストファイルに未コミット変更があれば、
  混ざらないようコミットか退避をユーザーに頼む
- デフォルトブランチ上なら作業ブランチ（例: `chore/test-prune`）を切る
- 中間ファイル（棚卸し表・カバレッジの出力）は scratchpad に置く。リポジトリには書かない

### 1. フェーズ0: 前提を自分で調べる（変更しない）

ユーザーに聞かずに調べて確定させ、根拠のファイル名と一緒に短くまとめる。

1. **言語・テストフレームワーク**: package.json / pyproject.toml / go.mod / Cargo.toml / pom.xml /
   build.gradle 等のマニフェストと、テストファイルの命名・配置から判断する
2. **テストコマンド**: マニフェストの scripts、Makefile / justfile / Taskfile、CI 設定（.github/workflows 等）、
   README・CONTRIBUTING から、プロジェクトが実際に使っているものを採る。モノレポなら対象パッケージごとに特定する
3. **カバレッジの取り方**: 既存の設定（vitest / jest の coverage、.coveragerc、pytest-cov、`go test -cover` 等）や
   CI での使われ方を探す。追加インストールなしで取れる方法を優先する。どうしても取れない場合は、
   その旨と代替の安全確認（テストの網羅関係を目視で追う等）を書く
4. **保護対象**: `references/categories.md` の「保護対象の探し方」に従って集める
5. テストとカバレッジを実際に一度実行し、コマンドが正しいことを確かめる。元から落ちるテストは記録し、手を出さない

### 2. フェーズ1: 棚卸し（変更しない）

1. 現状のテスト件数・テストコード行数・実行時間・行/分岐カバレッジ（あれば変異スコア）を記録する
2. 各テストを `references/categories.md` の A〜I / K に分類し、次の形式で一覧にする:
   `ファイル:行 | テスト名 | 分類 | 根拠（同じ保証をしているテスト名 or 保証している層） | 処置案`
3. 重複は「同じ行・分岐を通る」だけで判定しない。assert の中身まで比べる（検証している性質が違えば別物）
4. テストごとのカバレッジ（per-test coverage・`--coverage` を 1 ファイルずつ・`go test -coverprofile -run` 等）が
   安く取れるなら、C（ほぼ重複）の候補絞り込みに使う。最終判断は assert の比較で行う

テストファイルが多い（概ね 30 ファイル超）ときは、ディレクトリ単位に分けて Agent ツール
（`subagent_type: general-purpose`）で並列に棚卸しさせてよい。プロンプトには、担当範囲・フェーズ0の結果・
`references/categories.md` のパス・上の一覧形式・「変更禁止、読み取りのみ」・「最終報告は日本語で」を含める。

### 3. フェーズ2: 提案して止まる

次をまとめて提示する:

- フェーズ0で確定した前提（言語・コマンド・カバレッジの取り方・保護対象とその根拠）
- 削除・統合・書き直しの件数見込み（カテゴリ別）と、保護対象に触れる変更が無いこと
- 棚卸し一覧（長ければ scratchpad のファイルに書き、パスと要約を示す）
- 「要確認」: 判断に迷うもの。勝手に消さない
- 提案だけするもの: 変異テストやカバレッジツールの導入、テストではなく型・スキーマ・lint で守るべき箇所

`report` 指定時はここで終える。そうでなければ AskUserQuestion で
「全部適用 / カテゴリを選んで適用 / 中止」を聞き、承認を待つ。

### 4. フェーズ3: 小さく適用

- 1 ファイル（または 1 カテゴリ）ずつ変更し、そのたびにテストとカバレッジを実行する
- テストが落ちた・カバレッジが下がった変更は即座に戻し、理由を記録する
- パラメータ化したケースには「何を確かめるケースか」が分かる名前を付ける（入力値の羅列にしない）
- セットアップの重複は、一部の値だけ上書きできるフィクスチャ / ファクトリ関数に寄せる
- 書き直す場合（A・B・G）は、期待値を実装からではなく仕様（関数名・ドキュメント・型・呼び出し元の使い方）から
  導く。仕様が読み取れないものは書き直さず「要確認」に回す
- コミットはユーザーの指示があるときだけ。指示があればカテゴリ単位で分けると戻しやすい

### 5. フェーズ4: 報告

- 前後比較の表: テスト件数 / テストコード行数 / 実行時間 / 行・分岐カバレッジ（可能なら変異スコア）
- カテゴリ別の削除・統合・書き直し件数
- 戻した変更とその理由
- 残した「要確認」と、型・スキーマ・lint で守るべきだと感じた箇所の提案
- 次の一手として `/commit` や `/pr` を案内する（実行はしない）
