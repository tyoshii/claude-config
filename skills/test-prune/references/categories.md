# test-prune 分類表と保護対象

## 分類

各テストを次のどれかに分類する（複数可）。

| ID | 種類 | 典型例 | 処置 |
|---|---|---|---|
| A | トートロジー | 実装から期待値を写した／モックに X を返させて X が返ることを確認 | 削除、または仕様由来の期待値で書き直し |
| B | モックの検証 | 呼び出し回数・順序・引数だけを assert し、結果の振る舞いを見ていない | 観測可能な結果の assert に置換、無理なら削除 |
| C | ほぼ重複 | 入力を少し変えただけで同じ分岐・同じ assert | パラメータ化テスト（テーブル駆動）に統合 |
| D | 他層で保証済み | 型・スキーマ検証・DB 制約・lint で既に弾かれる前提条件 | 削除 |
| E | フレームワーク／ライブラリの動作確認 | 標準ライブラリやフレームワークが正しく動くことを確かめているだけ | 削除 |
| F | 定数・設定の鏡写し | 定数や設定値をそのままもう一度書いて一致を確認 | 削除（意図的な固定が必要なら 1 件に集約） |
| G | 実装詳細への密結合 | private 関数・内部状態・DOM 構造・CSS クラス・文言の完全一致・ソースの文字列 grep | 公開インターフェース経由の振る舞いテストに置換、無理なら削除 |
| H | 責務外 | テスト対象以外のモジュールの振る舞いを検証 | そのモジュールのテストへ移すか削除 |
| I | 価値の低い異常系 | 実運用で起きない入力の網羅、境界値の総当たり | 代表 1 件に絞る |
| K | 残す | 上記に当たらない／保護対象 | 変更なし（セットアップの重複はフィクスチャへ寄せてよい） |

## 保護対象（削除しない。統合・書き直しは可）

- セキュリティ・認可・権限境界（他人のデータへのアクセス拒否、署名検証、CSRF、入力のサニタイズ等）
- 過去のバグのリグレッションテスト（コメント・コミット履歴・issue 番号から判断）
- 永続化・マイグレーション・課金・外部 API やワイヤ形式の契約
- 並行処理・競合状態（各 1 件は残す）
- フェーズ0で見つけたプロジェクト固有の保護対象

## 保護対象の探し方

- CLAUDE.md / AGENTS.md / .cursor/rules / .claude/rules / CONTRIBUTING / README などのエージェント向け・
  開発者向けルール（「削除しない」「不変条件」「リグレッション」等の記述）
- ファイル名・describe 名に security / auth / permission / invariant / regression / migration / billing /
  contract を含むテスト
- issue 番号・バグ報告・日付付きの経緯コメントを持つテスト
- `git log` で fix: / bug / regression を含むコミットと一緒に追加されたテスト
  （例: `git log --format='%h %s' -i -E --grep='fix|bug|regression' -- <テストのパス>`）

## 背景（なぜ間引くか）

- **トートロジー化**: 実装を見てから書かせると、期待値が実装から写される。「コードはコードどおりに動く」を
  確かめるだけで、バグがあっても落ちない
- **過剰モック**: コーディングエージェントのテストコミットの 36% がモックを追加（人間は 26%）。
  モックの期待値も自分の実装の呼び出しのコピーになりやすい
- **実際の削減例**: 902→629 件、1827→1043 件の削減 PR がある。消したのは、ほぼ重複の組み合わせ、
  モックの呼び出し回数・順序、DOM/CSS/文言の確認、ソースの文字列 grep、定数の鏡写し、フレームワーク自体の
  動作確認。認証・課金・永続化・セキュリティ境界・プロトコル契約・競合状態は残した
- **安全網**: テストごとのカバレッジで重複候補を絞り、前後でカバレッジが下がらないことを条件にする。
  ただし重複率が高くても assert が違えば別物なので、最終判断は人がする
- **「テストしない」判断**: 型・スキーマ・DB 制約・lint ですでに保証されていることは、テストを重ねない
